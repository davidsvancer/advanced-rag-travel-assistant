# Advanced RAG Travel Agency Assistant

A research-oriented travel agency chatbot developed as part of my Bachelor's thesis at Brno University of Technology (FIT VUT). The project explores how different retrieval techniques affect the quality of answers generated by a Retrieval-Augmented Generation (RAG) system.

The assistant answers questions about accommodation and general travel-agency topics. It combines structured accommodation data with unstructured guest reviews and FAQ content, retrieves relevant information from Weaviate, and uses a local large language model to generate context-grounded responses.

## Key Features

- **Semantic query routing** – classifies incoming questions and directs them to the accommodation or FAQ collection.
- **Hybrid retrieval** – combines vector similarity search and BM25 keyword search through Weaviate.
- **Multi-Query Retrieval** – generates alternative formulations of the user's question to broaden the retrieval scope.
- **Cross-encoder reranking** – reorders retrieved candidates using `BAAI/bge-reranker-base` and selects the most relevant context.
- **Conversation history** – rewrites follow-up questions into standalone queries before retrieval.
- **Configurable pipeline** – allows retrieval components, embedding models, and retrieval parameters to be changed from the command line.
- **RAGAS evaluation** – evaluates generated answers and retrieved context using five metrics.
- **Statistical analysis** – compares configurations using paired bootstrap confidence intervals and generates evaluation plots.

## Architecture

The application uses two Weaviate collections:

- `BNB` – accommodation listings, descriptions, amenities, prices, and aggregated guest reviews.
- `FAQ` – frequently asked questions about general travel-agency topics, such as bookings, cancellations, luggage, insurance, and payments.

The request-processing flow is:

```text
User query
    |
    v
Semantic router (Llama 3)
    |
    +-----------------------+
    |                       |
    v                       v
BNB collection          FAQ collection
    |                       |
    +-----------+-----------+
                |
                v
       Configurable retrieval
       - Vector / BM25 / Hybrid
       - Optional Multi-Query
       - Optional cross-encoder reranking
                |
                v
       History-aware retrieval
                |
                v
       LLM answer generation
                |
                v
          Chat response
```

The retrieval pipeline is modular. Multi-Query Retrieval and reranking can be enabled independently. The `--alpha` parameter controls the Weaviate hybrid-search balance: `1.0` means vector-only search, `0.0` means BM25-only search, and `0.5` combines both.

## Requirements

The project was developed with Python 3.11 and uses the dependencies pinned in `requirements.txt`.

You will need:

- Python 3.11
- Docker and Docker Compose
- Ollama
- Sufficient memory and compute resources to run the selected local language, embedding, and reranking models
- An OpenAI API key to run the RAGAS evaluation

## Setup

### 1. Create a virtual environment

From the repository root:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
```

Install the dependencies:

```bash
pip install -r requirements.txt
```

### 2. Start Weaviate

Start the local Weaviate instance:

```bash
docker compose up -d
```

The provided Docker Compose configuration exposes Weaviate on ports `8080` and `50051` and stores its data in a Docker volume.

### 3. Prepare Ollama models

Make sure the Ollama service is running, then download the chat and embedding models:

```bash
ollama pull llama3
ollama pull bge-m3
ollama pull nomic-embed-text
```

The default embedding model is `bge-m3`. `nomic-embed-text` is available for comparison.

## Create the Weaviate Collections

The database preparation script loads the accommodation listings and reviews, combines selected listing information with guest reviews, prepares FAQ documents, and creates the `BNB` and `FAQ` collections in Weaviate.

Run it from the `src/chatbot` directory because the script uses paths relative to that working directory:

```bash
cd src/chatbot
python create_database.py
```

To select an embedding model explicitly:

```bash
python create_database.py --model bge-m3
```

Available parameter:

| Parameter | Description | Default |
|---|---|---|
| `--model` | Ollama embedding model used to create document embeddings. | `bge-m3` |

**Important:** The embedding model used to create the collections must match the model used later by the chatbot for retrieval. If you switch embedding models, recreate the collections with the selected model.

## Run the Chatbot

Run the interactive command-line chatbot from `src/chatbot`:

```bash
cd src/chatbot
python chatbot.py
```

The default configuration uses vector-only retrieval (`--alpha 1.0`), BGE-M3 embeddings, and retrieves three candidates.

### Command-line Options

| Parameter | Description | Default |
|---|---|---|
| `--use-multiquery` | Enables Multi-Query Retrieval. | Disabled |
| `--use-reranker` | Enables cross-encoder reranking. | Disabled |
| `--alpha` | Weaviate hybrid-search balance: `1.0` vector-only, `0.0` BM25-only, `0.5` hybrid. | `1.0` |
| `--base-k` | Number of initial candidate documents retrieved. | `3` |
| `--top-k` | Number of documents retained by the reranker. | `3` |
| `--embeddings` | Ollama embedding model used for retrieval (`bge-m3` or `nomic-embed-text`). | `bge-m3` |

### Example: Hybrid Search

```bash
python chatbot.py --alpha 0.5 --base-k 10
```

### Example: Full Retrieval Pipeline

The final experimental configuration uses hybrid search, Multi-Query Retrieval, and reranking. It retrieves a larger candidate set and then keeps the top three documents after reranking:

```bash
python chatbot.py \
    --use-multiquery \
    --use-reranker \
    --alpha 0.5 \
    --base-k 15 \
    --top-k 3 \
    --embeddings bge-m3
```

The first run with reranking may download `BAAI/bge-reranker-base` from Hugging Face. An internet connection is required unless the model is already available in the local Hugging Face cache.

Exit the interactive chatbot by entering `exit`, `bye`, `end`, or `quit`.

## Evaluation

The project includes a custom evaluation dataset containing 310 questions. The questions cover several retrieval and reasoning challenges, including basic factual queries, vague questions, negation, multi-hop questions, and false-premise questions.

The RAGAS evaluation pipeline:

1. Loads the evaluation questions and reference answers.
2. Runs each question through the configured chatbot retrieval and generation pipeline.
3. Collects the generated answer and retrieved context.
4. Evaluates the results using GPT-4o-mini as an LLM judge.

The following RAGAS metrics are calculated:

- **Faithfulness** – whether the generated answer is supported by the retrieved context.
- **Answer Relevancy** – how relevant the generated answer is to the original question.
- **Context Precision** – how much of the retrieved context is relevant.
- **Context Recall** – whether the retrieved context contains the information needed to answer the question.
- **Answer Correctness** – how well the generated answer matches the reference answer.

### Configure the OpenAI API Key

Set the API key in your environment:

```bash
export OPENAI_API_KEY="your-api-key"
```

Alternatively, the evaluation script loads environment variables from a `.env` file in the current working directory. Do not commit API keys or `.env` files to the repository.

### Run RAGAS Evaluation

Run the evaluation module from the repository root:

```bash
python -m src.eval.ragas_eval --output results/evaluation.csv
```

The same retrieval options available in the chatbot can be used:

```bash
python -m src.eval.ragas_eval \
    --use-multiquery \
    --use-reranker \
    --alpha 0.5 \
    --base-k 15 \
    --top-k 3 \
    --embeddings bge-m3 \
    --output results/full_rag_bge.csv
```

The evaluation script uses the OpenAI API for judging, so API usage may incur costs.

## Router Evaluation

The semantic router can be evaluated separately on the question dataset:

```bash
python -m src.eval.router_eval --output results/router_predictions.csv
```

Options:

| Parameter | Description |
|---|---|
| `--output` | CSV file where router predictions are saved. Required. |
| `--question-column` | Name of the input question column. Defaults to `question`. |

The output CSV contains the original dataset columns and an additional `router_prediction` column.

## Statistical Comparison

The `compare_stats.py` utility performs paired bootstrap comparisons between two evaluation result files. It calculates metric means, confidence intervals for the paired differences, and a bootstrap p-value. The default number of bootstrap iterations is 10,000.

Run it from `src/util`:

```bash
cd src/util

python compare_stats.py \
    --file_a ../../results/hybrid_bge.csv \
    --file_b ../../results/reranker_bge.csv \
    --name_a Hybrid \
    --name_b Full_RAG \
    --by_category
```

Useful options:

| Parameter | Description |
|---|---|
| `--file_a` | First evaluation result CSV. Required. |
| `--file_b` | Second evaluation result CSV. Required. |
| `--name_a` | Label for the first configuration. |
| `--name_b` | Label for the second configuration. |
| `--by_category` | Also performs comparisons for individual question categories. |
| `--category_output` | Output CSV for category-level comparisons. |
| `--output` | Output CSV for overall comparisons. |
| `--metrics` | Metrics to compare. |
| `--n_bootstrap` | Number of bootstrap iterations. Defaults to `10000`. |
| `--seed` | Random seed. Defaults to `42`. |

The comparison is based on paired rows, so both input files must contain corresponding questions in the same order.

## Experimental Results

The following table summarizes the aggregate results stored in the repository's evaluation CSV files. Scores range from `0` to `1`; higher values are better.

| Configuration | Faithfulness | Answer Relevancy | Context Precision | Context Recall | Answer Correctness |
|---|---:|---:|---:|---:|---:|
| Hybrid Search (BGE-M3) | 0.7520 | 0.4571 | 0.4956 | 0.5274 | 0.5048 |
| Hybrid + Multi-Query (BGE-M3) | 0.6748 | 0.5333 | 0.4887 | 0.6149 | 0.4700 |
| Full RAG + Reranker (BGE-M3) | **0.7804** | **0.5445** | **0.6144** | 0.5909 | **0.6112** |

In the evaluated dataset, the full configuration achieved the strongest results in four of the five aggregate metrics. Multi-Query Retrieval increased context recall, while reranking improved context precision and answer correctness. The results are specific to this dataset and experimental setup; they should not be interpreted as a general guarantee of performance.

## Limitations

- The knowledge base is based on a fixed accommodation and FAQ dataset; it does not provide live availability, booking, or price updates.
- The system's answers depend on the quality and coverage of the source data and retrieved context.
- Running local LLMs, embedding models, and a cross-encoder reranker requires suitable local hardware resources.
- The RAGAS evaluation uses an LLM judge, so its scores are automated estimates rather than human ground truth.
- Latency and production-scale performance were not systematically evaluated.
